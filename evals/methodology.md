# Evaluation Methodology

## What This Document Covers

This document describes how family accuracy figures are measured, stored, and
maintained for Example Reviewer. It backs the claims in
[README.md Section 9](../README.md#9-supported-families) and the data in
[evals/family_accuracy_report.json](family_accuracy_report.json).

## Definitions

**Discovered**
The count of code examples extracted from documentation source files during
Phase A (Discovery). Determined by the family's `content_roots` configuration
in `config/families/<family>.json`.

**Verified**
An example reaches `VERIFIED` status after passing all three evidence gates:

1. **Phase B — Compilation gate**: the example compiles successfully with `dotnet build`
   against the configured NuGet package version (either the original code, or a
   deterministic/LLM-assisted fix).
2. **Phase C — Runtime gate**: the compiled binary runs to completion without
   unhandled exceptions (using the 5-tier fixture resolver to supply required files).
3. **Phase E — Final review gate**: the LLM reviewer confirms the fixed code still
   demonstrates the same API functionality as the original (semantic fidelity check).

All three must pass. An example that compiles but fails at runtime is not `VERIFIED`.

**Verification rate**
`verified / discovered × 100`, rounded to one decimal place.

**Failed**
Examples that did not reach `VERIFIED` after all fix attempts. Includes
`COMPILE_FAILED` (could not be fixed), `RUNTIME_FAILED`, and `REVIEW_FAILED`
sub-states.

## Baseline Generation

Baselines are generated by `scripts/evals/generate_baseline.py`, which reads
from the production SQLite database using `ResultsSummary.from_run()` and
`Database.get_run_stats_from_db()`.

When the production DB is not available (CI environment, dev machine without
sync), the script falls back to figures documented in README Section 9, which
originate from the same production runs. These are marked
`"source": "readme_documented_production_run"` in the JSON.

### Running baseline generation

```bash
# Single family from production DB
python scripts/evals/generate_baseline.py --family zip --db-path data/example_reviewer_prod.db

# All families from documented figures (CI-safe, no DB required)
python scripts/evals/generate_baseline.py --all

# All families from production DB
python scripts/evals/generate_baseline.py --all --db-path data/example_reviewer_prod.db
```

Output: `.benchmarks/baselines/<family>_baseline.json`

## Update Frequency

Baselines should be refreshed whenever:

- A pipeline change could affect compile, runtime, or review outcomes
- A family's NuGet package version is updated
- A new family is added to production
- Quarterly (at minimum), before the review snapshot window

After refreshing, commit the updated files and update `report_date` in
`evals/family_accuracy_report.json`.

## Interpreting the Unverified Fraction

Not all unverified examples represent pipeline failures. Common reasons:

| Reason | Category | Typical cause |
|--------|----------|--------------|
| API removed in newer package version | COMPILE_FAILED | Method/type deleted in latest NuGet |
| Missing external resource | RUNTIME_FAILED | Required file not resolvable by 5-tier fixture chain |
| Fundamentally broken original | COMPILE_FAILED | Example was never correct; LLM cannot reconstruct intent |
| Semantic drift exceeds tolerance | REVIEW_FAILED | Fix changed the demonstrated API function |

The `docs/accuracy-audit.md` file contains the per-family breakdown of unverified
cases for the top families.

## CI Integration

The `eval-baseline-check` job in `.gitlab-ci.yml` runs two checks:

1. `scripts/evals/check_eval_freshness.py` — fails if `report_date` in
   `evals/family_accuracy_report.json` is older than 90 days.
2. `scripts/evals/validate_eval_claims.py` — cross-validates README Section 9
   accuracy figures against `evals/family_accuracy_report.json` and exits non-zero
   if any family diverges by more than 1%.

Both jobs use `allow_failure: true` initially to warn without blocking merges.
